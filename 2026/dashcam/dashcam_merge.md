# dashcam_merge.py — склейка записей видеорегистратора по поездкам

Скрипт собирает файлы регистратора (Thinkware U3000, но подойдёт любой с похожей
схемой именования) в один mp4 на каждую поездку. Видео, звук и дорожка субтитров
с телеметрией (G-сенсор + GPS) сохраняются. Дополнительно рядом с каждым mp4
пишутся `.srt` (телеметрия в читаемом виде) и `.gpx` (GPS-трек).

## Требования

- `python3` (3.8+, только стандартная библиотека)
- `ffmpeg` в PATH; для режима `--encode` нужна сборка с `libx265`

## Что должно быть на входе

Файлы вида `REC_YYYYMMDD_HHMMSS_F.MP4` и `EVT_YYYYMMDD_HHMMSS_F.MP4`
в одной или нескольких папках (например, `cont_rec/` и `evt_rec/`).

- `REC_*` — непрерывная запись (по умолчанию 60 с на файл).
- `EVT_*` — запись по событию (удар, кочка): ~10 с до и ~10 с после срабатывания.
  Первая половина дублирует REC, вторая закрывает дыру, пока REC не возобновится.
- Суффикс `_F` / `_R` — камера. Каждая камера обрабатывается отдельно и получает свой набор файлов.
- Префикс `REC`/`NOR`/`NORMAL`/`MOV`/`MOVIE` считается обычной записью, любой другой — событийной.

## Быстрый старт

```bash
cd /папка/с/архивом

# 1. Посмотреть план: какие поездки получатся и из каких кусков
python3 dashcam_merge.py cont_rec evt_rec --dry-run -v

# 2а. Склеить без перекодирования (быстро, ~15x realtime, размер как у исходников)
python3 dashcam_merge.py cont_rec evt_rec -o merged

# 2б. Склеить и пережать x265 (медленно, ~0.8x realtime, файлы в 4–6 раз меньше)
python3 dashcam_merge.py cont_rec evt_rec -o merged_x265 --encode --crf 22
```

Долгий запуск лучше пускать в фоне, чтобы пережил закрытие терминала:

```bash
setsid nohup python3 dashcam_merge.py cont_rec evt_rec -o merged_x265 --encode \
    > merged_x265.log 2>&1 < /dev/null &
tail -f merged_x265.log      # прогресс ffmpeg и итоги по поездкам
```

## Что получается на выходе

В папке `-o` для каждой поездки и камеры:

| Файл | Содержимое |
|---|---|
| `TRIP_YYYYMMDD_HHMMSS_F.mp4` | видео + звук + дорожка субтитров с телеметрией (mov_text) |
| `TRIP_YYYYMMDD_HHMMSS_F.srt` | та же телеметрия в виде обычных субтитров, без служебных тегов |
| `TRIP_YYYYMMDD_HHMMSS_F.gpx` | GPS-трек: координаты, время UTC, скорость (м/с в `<extensions>`) |

Время в имени — начало поездки по часам регистратора. Если часы регистратора
были сбиты до первого GPS-фикса, скрипт это обнаруживает и использует
исправленное время (так что файл от «31 августа» может лечь в поездку 2 сентября,
если он на самом деле оттуда).

Уже существующие выходные файлы пропускаются, если не указан `--overwrite`.

## Параметры

| Параметр | По умолчанию | Что делает |
|---|---|---|
| `dirs` (позиционные) | — | папки и/или отдельные файлы с записями; можно несколько |
| `-o`, `--out DIR` | `merged` | папка для результата (создаётся сама) |
| `--gap SEC` | `300` | пауза в записи больше этого числа секунд начинает новую поездку |
| `--evt-lead SEC` | `9` | на сколько секунд EVT-файл начинается раньше времени в своём имени; используется только если в файлах нет GPS (иначе вычисляется само) |
| `--prefix STR` | `TRIP` | префикс имён выходных файлов |
| `--encode` | выкл | пережать видео libx265; звук и субтитры копируются как есть |
| `--crf N` | `22` | качество x265 при `--encode`; больше = меньше файл. 22 — без видимой потери, 24 — ещё минус 30 % |
| `--preset NAME` | `medium` | preset x265 при `--encode` (`slow` даст ещё ~10 % экономии за ~2x время) |
| `--no-srt` | | не писать `.srt` |
| `--no-gpx` | | не писать `.gpx` |
| `--faststart` | выкл | перенести moov в начало файла (удобно для стриминга; второй проход по файлу) |
| `--overwrite` | выкл | пересобрать уже существующие результаты |
| `--dry-run`, `-n` | | только показать план, ничего не записывать |
| `--slow` | выкл | разбирать файлы через ffprobe/ffmpeg вместо встроенного парсера mp4 (на порядок медленнее, но универсально) |
| `-v`, `--verbose` | | подробный вывод: выравнивание каждого файла, список кусков, ffmpeg-список кусков не удаляется |

## Как читать вывод `--dry-run -v`

```
clock: gps-name offset rec=-3599.8s evt=-3608.9s (evt lead 9.1s)
REC_20260902_205915_F.MP4  rec start=20:59:15.0 dur= 50.0 subs= 500 kf= 50 align=gps
EVT_20260902_210004_F.MP4  evt start=20:59:54.9 dur= 20.0 subs= 200 kf= 20 align=gsensor(101, vs REC_..., shift +1.0s)
...
--- поездка 1/3: TRIP_20260902_205417_F  файлов=81 кусков=65 длительность=31.7 мин  дыр=2
    [gap] нет записи 21:06:28 -> 21:06:29 (0.1s)
    00:00:00,000  REC_20260831_204050_F.MP4   0.000 ->  60.000 ( 60.0s)
    00:03:47,200  EVT_20260831_204437_F.MP4   9.000 ->  19.800 ( 10.8s)
```

- `align=` — как файл поставлен на шкалу времени: `name` (по имени файла, ±1 с),
  `gps` (по медиане GPS-времени из субтитров), `gsensor(N, vs X, shift S)` — по совпадению
  N отсчётов G-сенсора с файлом X (самый точный способ, 0.1 с), `name+NNNs(clock jump)` —
  имя файла скорректировано из-за скачка часов регистратора.
- `[gap]` — участок, который не покрыт ни одним файлом. Дыры по 0.1 с — норма
  (регистратор теряет несколько кадров при переключении файла). Большие дыры — регистратор
  реально не писал (стоянка, выключение).
- Строки кусков: время в выходном файле, исходный файл, `in -> out` в секундах исходника.
  Каждый кусок начинается с ключевого кадра, поэтому стыки идут без перекодирования.

## Как это работает (если понадобится чинить)

1. Для каждого файла напрямую читается moov-атом: длительность, ключевые кадры,
   все сэмплы дорожки субтитров. ffprobe не вызывается, поэтому 170 файлов
   разбираются за секунды (на sshfs без кэша — около 1.5 с на файл).
2. Файлы ставятся на общую шкалу времени тремя способами по убыванию точности:
   совпадение отсчётов G-сенсора с пересекающимся соседом, медиана GPS-времени
   из GNRMC-строк, время из имени файла. Скачок часов регистратора (до GPS-фикса)
   компенсируется поправкой из ближайшего следующего файла с GPS.
3. Поездки разделяются по паузам больше `--gap`.
4. Жадный обход: держимся текущего файла до его конца, затем берём тот из покрывающих
   момент файлов, который тянется дальше всех (REC предпочтительнее при равенстве).
   Начала кусков сдвигаются на ключевые кадры, конец предыдущего куска подстраивается,
   чтобы время шло непрерывно.
5. Один вызов ffmpeg с concat demuxer (`inpoint`/`outpoint`) и `-c copy`
   либо `-c:v libx265 -c:a copy -c:s copy` при `--encode`.

Известные особенности:

- На стыках ffmpeg пишет `Non-monotonic DTS in output stream 0:1` — это перекрытие одного
  аудиопакета (21 мс), которое он сам исправляет. Не ошибка.
- В GNRMC-строках регистратора время иногда сбивается на секунду или повторяется, поэтому
  берётся медиана по файлу, а не первая строка.
- Исходные файлы регистратора предаллоцированы (у всех одинаковый размер, хвост — пустой
  `free`-атом). Реальный объём видео меньше размера файла.

## Результаты на архиве 2026-09-03 (для ориентира)

| Поездка | Без перекодирования | x265 crf 22 medium | Время кодирования |
|---|---|---|---|
| 31.7 мин | 5.34 GiB | 1.14 GiB | 41 мин |
| 15.3 мин | 2.59 GiB | 0.41 GiB | 18 мин |
| 32.0 мин | 5.39 GiB | 1.12 GiB | 41 мин |

Сравнение кодеков на ночных клипах: NVENC HEVC при равном размере заметно хуже по SSIM,
NVENC AV1 и SVT-AV1 дают чуть лучше x265, но вдвое дольше и не везде воспроизводятся.
Визуально при crf 22–24 отличий от исходника не видно: ограничение — шум и смаз самой камеры.
